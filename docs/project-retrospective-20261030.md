# doc-agent 개발 회고

작성일: 2026-10-30

이 프로젝트에서 내가 집중한 일은 팀원이 학습한 객체 탐지 모델을 실제 문서 처리 흐름에 연결하고, 인식 결과를 사용자가 믿고 들을 수 있는 안내로 만드는 것이었다. 개발은 탐지 모델 연결, OCR과 항목 구조화, 실제 문서 검증, 안내 방식 재설계, 검수·평가 도구 구축, 인식 개선 실험 순서로 진행했다.

아래 내용은 당시 코드와 저장된 실험 결과를 바탕으로 정리했다. 팀원에게 전달받은 모델 학습 수치와 직접 수행한 연동 실험은 구분했다. 현재는 공통 처리 기능을 구현하고 실제 지원 문서의 원문·정답을 검수하는 단계이며, 최종 서비스 정확도를 확보한 상태는 아니다.

## 1. 먼저 작성 영역을 찾는 기능부터 연결했다

시각장애인의 종이문서 작성을 돕기 위해서는 문서에 어떤 항목이 있고 어디를 체크하거나 서명해야 하는지 알아야 했다. 그래서 처음부터 문서 전체를 자유롭게 해석하려 하기보다, 체크박스와 서명란의 위치를 찾는 기능을 출발점으로 삼았다.

모델 학습은 팀원이 담당했다. 국내 문서를 수집하고 실제 선택 기능이 있는 체크박스와 서명란을 수작업으로 라벨링했다. 이름이나 전화번호를 쓰는 일반 사각형 입력칸은 체크박스에서 제외했다. 처음에는 74장으로 학습했고, 서명란을 놓치는 문제를 확인한 뒤 106장으로 데이터를 보강했다.

초기에 공유받은 모델 개발 결과는 다음과 같았다.

| 구분 | 데이터 수 | mAP@50 | F1 | Recall |
|---|---:|---:|---:|---:|
| 초기 모델 | 74장 | 약 79.0% | 약 74.8% | 약 70.0% |
| 데이터 보강 후 | 106장 | 약 81~82% | 약 80% | 약 90% |

이 수치는 팀원의 모델 개발 보고 기준이다. 내가 코드 연동 과정에서 다시 측정한 결과는 아니며, 두 모델의 테스트 구성도 달라 같은 고정 시험에서의 개선 폭으로 단정할 수는 없었다.

탐지에는 이미 학습된 **RF-DETR NAS 모델과 Roboflow API**를 활용했다. 모델 학습 결과가 확보돼 있었기 때문에, 우선 그 결과를 실제 입력과 후속 처리에 연결하는 데 집중할 수 있었다. 별도의 모델 비교 실험을 새로 한 것은 아니므로 RF-DETR가 모든 대안보다 좋다고 판단한 것은 아니다.

연결하면서는 API를 호출하는 것 외에도 응답 형식을 맞추는 작업이 필요했다. 도구마다 체크박스 클래스 이름과 번호가 달랐기 때문에 클래스 이름을 기준으로 내부 유형에 대응시켰다. 이미지의 픽셀 좌표는 A4 문서의 mm 좌표로 변환했다. 이후 해상도가 다른 입력이나 위치 안내 기능을 연결할 때 좌표 기준이 달라지지 않도록 하기 위해서였다.

한 번은 Workflow의 기본 모델 설정으로 추론했을 때 탐지가 0건이었다. 이를 바로 모델의 미탐 문제로 해석하지 않고 연결된 모델부터 확인했고, 실제 학습된 모델을 명시하도록 바꿨다. 이 과정에서 **모델 자체의 성능 문제와 모델을 잘못 연결한 문제를 먼저 구분해야 한다**는 점을 배웠다.

## 2. 위치를 찾은 뒤에는 주변 글자를 읽고 연결해야 했다

체크박스 좌표만으로는 그 항목이 개인정보 동의인지, 전입 사유인지 설명할 수 없었다. 그래서 탐지 영역 주변을 잘라 글자를 읽고 박스와 문구를 연결하는 OCR 단계를 추가했다.

OCR은 **Tesseract의 한국어·영어 인식**을 사용했다. 로컬에서 실행할 수 있고 단어별 좌표와 신뢰도를 받을 수 있어, 탐지 결과와 연결하기에 적합했다. OCR 전용 외부 호출 없이 반복 실험할 수 있다는 점도 이 구성을 유지한 이유였다. 다만 Roboflow 탐지에는 별도로 이미지 전송이 필요하므로, OCR이 로컬이라는 이유로 전체 처리가 로컬이라고 보지는 않았다.

처리 방식은 탐지된 영역 주변만 읽는 `regions`와 전체 페이지를 읽는 `page`로 나눴다. 주변 영역만 읽으면 작성 항목에 집중할 수 있지만 제목이나 약관이 빠질 수 있었다. 반대로 전체 페이지를 읽으면 더 많은 문구를 확보하지만 어느 문구가 어느 박스에 속하는지 연결하는 일이 어려워졌다.

나는 Crop 안에서 인식한 단어 좌표를 전체 문서 좌표로 복원하고, 체크박스 좌우의 문구와 서명란 왼쪽·위쪽의 문구를 비교하도록 구현했다. 문구가 없거나 서명 주체가 모호하면 내용을 만들어 채우지 않고 미확정 상태와 검토 경고를 남겼다.

이때부터 탐지, OCR, 항목 해석의 신뢰도를 따로 보존했다. 박스를 잘 찾았더라도 글자를 잘못 읽을 수 있고, 글자를 잘 읽었더라도 다른 항목에 연결할 수 있기 때문이다. 숫자 하나로 전체 처리가 정확하다고 표시하면 어느 단계에서 문제가 생겼는지 파악하기 어려웠다.

## 3. 실제 문서를 넣으면서 입력 처리의 문제를 발견했다

공유받은 문서는 원본과 출력 후 촬영한 사진이 섞여 있었다. 동일 파일을 제외하고 PDF를 페이지별 이미지로 변환해 총 299페이지를 분석했다. 촬영본은 별개의 양식으로 세지 않고 대응하는 원본과 묶었다.

| 입력 | 전체 페이지 | 탐지 후보 있음 | 탐지 후보 없음 | 최종 실행 오류 |
|---|---:|---:|---:|---:|
| 원본 | 162 | 119 | 43 | 0 |
| 촬영본 | 137 | 118 | 19 | 0 |
| 합계 | 299 | 237 | 62 | 0 |

전체 수집 파일은 219개였고, 동일한 중복 46개를 제외한 173개 파일에서 위 페이지를 구성했다. 촬영본 137페이지는 원본 85페이지에 대응했다. 중간 API 오류 한 건은 재시도 후 처리됐다.

이 실행으로 연동 동작은 확인했지만 정확도는 계산하지 못했다. 정답 박스와 정답 텍스트가 없었고 학습 자료와의 중복도 확인되지 않았기 때문이다. 탐지 후보가 없는 62페이지에는 안내문이나 법령 본문도 있어 모두 미탐이라고 볼 수 없었다.

실제 입력에서는 다음 문제가 특히 컸다.

### 문서 안의 표를 종이 테두리로 잘못 인식했다

이미지 정합 과정에서 문서 안의 큰 표를 종이 경계로 선택해 제목이나 하단 서명란이 잘리는 문제가 있었다. 이후 탐지 모델은 이미 잘린 이미지를 받기 때문에, 모델을 조정하는 것만으로 해결할 수 없는 문제였다.

A4 비율과 밝은 바깥 여백을 확인할 수 있는 원본은 페이지 전체를 유지하도록 바꿨다. 당시 원본 154페이지가 이 조건에 해당했고 촬영본은 해당하지 않았다. 전체 페이지를 유지하는 대체 처리였으므로 종이 경계를 정확히 찾았다고 표시하지 않고 낮은 정합 신뢰도와 검토 경고를 남겼다.

이 경험 이후에는 탐지 결과가 나쁘면 모델보다 먼저 **입력이 잘렸는지, 기울어졌는지, 좌표 변환이 맞는지**를 확인하게 됐다.

### 이미지 분석이 불필요한 대화 초기화에 걸렸다

기존 흐름은 이미지 분석과 대화 세션 생성을 함께 수행했다. 단순히 탐지와 OCR만 실행하려는 경우에도 LLM 전송용 개인정보 검사가 실행됐고, 항목 ID와 OCR 숫자의 조합이 전화번호처럼 판단돼 중단되는 사례가 있었다.

검사를 느슨하게 하는 대신 이미지 분석을 `analyze_document()`로 분리했다. 분석 CLI는 탐지·OCR·구조화만 수행하고, 실제 대화 세션을 만들 때 필요한 전송 검사는 유지했다. 처리 목적에 따라 책임을 나누는 편이 원인을 추적하고 재검증하기 쉬웠다.

### 탐지 개수가 나와도 항목 연결은 불완전했다

체크박스처럼 보이는 글자를 박스로 오인하거나 전화번호 표시를 서명란으로 오인하는 사례가 있었다. 선택지 문구가 빈 결과도 원본은 1,088개 중 263개, 촬영본은 1,235개 중 445개였다.

두 집단의 양식 구성이 달라 이 차이를 촬영에 따른 정확도 하락률로 계산하지는 않았다. 다만 탐지 결과를 그대로 음성 안내에 넘기기에는 문구 누락과 항목 연결 문제가 남아 있다는 근거는 됐다. 정답 데이터 준비를 연동 실험과 함께 시작했어야 했다는 아쉬움도 남았다.

## 4. 안내 방식을 생성형 설명에서 검토된 원문 낭독으로 바꿨다

초기에는 탐지와 OCR 결과를 LLM에 전달해 문맥을 이해하고 설명하게 하는 방향을 고려했다. 그러나 문서의 내용을 임의로 요약하거나 작성 방법을 만들어내면 안 된다는 피드백을 받았다. 조건이나 예외가 빠진 설명은 사용자의 실제 선택에 영향을 줄 수 있었다.

그래서 지원 문서를 제한하고, 사람이 원문을 검토한 안내 데이터를 미리 등록하는 방향으로 바꿨다. 문서 ID·버전·페이지·항목 유형과 OCR 키워드로 해당 항목을 찾고, 등록된 문구를 반환하는 **Rule 기반 매칭**을 우선 구현했다.

이 방식은 어떤 조건으로 안내가 선택됐는지 추적하기 쉬웠다. 문서 수가 적고 검수 데이터도 아직 없는 상황에서 의미 검색까지 동시에 도입하면, OCR 오류와 검색 오류 중 무엇을 고쳐야 하는지 구분하기 어려울 것으로 판단했다. 임베딩 기반 RAG는 이후 검색을 확장할 수단으로 남겨뒀다. 저장소에 있던 개발용 RAG 코드와 실제 승인 안내 검색은 별도로 다뤘다.

처음에는 사람이 작성한 고정 설명문을 그대로 읽는 방식이었다. 이후 요구가 더 분명해졌다. **검토된 설명문이라도 원문을 축약해서는 안 되고, 해당 원문 전체를 읽어야 했다.**

이에 검색용 주변 문구와 낭독용 원문을 분리하고, 실제 안내 문장이 낭독 원문 전체와 정확히 같아야 승인할 수 있도록 바꿨다. 항목별 읽기에 더해 페이지 전체·문서 전체 읽기를 구현했다. 문서 전체 읽기는 전체 페이지 수와 모든 페이지의 승인 여부를 확인한 뒤 제공한다.

여기서 ‘원문 그대로’는 OCR 문자열을 즉시 읽는다는 뜻이 아니다. 잘못 인식한 글자를 그대로 읽는 문제를 피하기 위해, **원본과 대조해 검토한 원문을 저장하고 그것을 읽는 구조**로 정리했다. PDF에서 추출한 텍스트도 표의 읽기 순서와 누락을 확인하기 전까지는 초안으로 남겼다.

## 5. 지원 문서와 평가 자료를 고르는 기준도 바뀌었다

처음에는 로컬 원본이 있고 Roboflow의 test에 들어 있는 문서 세 종을 후보로 잡았다. 예술인 관련 확인서와 진료기록 동의서·위임장이었다. 원문·라벨·OCR·안내 초안을 함께 보는 검수 자료를 만들기에는 적합했지만, 모든 학습 이력에서 제외된 양식이라고 확정할 수는 없었다.

실제로 원본 문서 묶음의 다른 페이지가 train과 test에 나뉜 사례를 확인했다. 파일명이 다른 촬영본도 같은 원본의 사본일 수 있었다. 따라서 **test 분할의 이미지라는 사실과 처음 보는 문서 양식이라는 사실을 구분**하기로 했다.

세 후보의 당시 로컬 실행은 OpenCV 휴리스틱과 Tesseract로 수행했다. 예술인 문서는 체크박스 후보 4개가 나왔지만 진료기록 두 문서에서는 서명 후보를 찾지 못했다. 이 결과를 RF-DETR의 성능으로 보고하지 않았다. 어떤 탐지기를 실행했는지와 수동으로 지정한 OCR 영역인지도 함께 기록했다.

이후 주민센터 문서로 범위를 좁히고 Roboflow의 원본명·버전별 분할과 불명확한 서식 화면을 추가 대조했다. v3 전체 106장의 이력, 그 안의 v2 이력, v1 학습 10장 등을 확인한 뒤 **전입신고서(세대 모두 이동)**를 추가 후보로 골랐다.

이 서식은 확인한 프로젝트 학습 이력에서 발견되지 않았다. 다만 기반 모델의 사전학습이나 다른 프로젝트·삭제된 이력까지 확인한 것은 아니다. 학습 제외 판단에도 확인 범위를 남겼다.

공식 빈 서식을 확보한 뒤에는 입력 해상도를 바꿔 실제 추론을 비교했다.

| 입력 | 체크박스 탐지 | 서명란 탐지 | OCR 단어 수 |
|---|---:|---:|---:|
| 1557×2200, 약 188dpi | 5개 | 1개 | 933개 |
| 2480×3505, 300dpi | 6개 | 2개 | 917개 |

최초 실행도 설정값은 300dpi였지만 원본 이미지의 실제 픽셀 밀도는 그보다 낮았다. 같은 PDF를 300dpi로 다시 렌더링했다. **설정에 적은 해상도와 입력이 가진 정보량은 다르다**는 점을 확인한 실험이었다.

이 문서에는 체크박스 8개와 서명 표시 3개의 참조 박스 초안을 준비했지만, 사람 검수가 끝난 정답은 아니다. 따라서 탐지된 8개를 참조 11개로 나눠 정확도나 Recall로 발표하지 않았다. 정합·OCR·항목 연결에도 경고가 남아 있어 실제 안내를 활성화하지 않았다.

또한 이 원본은 이미 해상도 조정과 안내 데이터 작성에 사용했다. 모델 학습에서 제외된 양식이라도 최종 평가까지 한 번도 사용하지 않은 자료는 아니었다. 최종 평가는 설정을 고정하고 개발에 쓰지 않은 별도 촬영본으로 수행하기로 했다.

## 6. OCR 전처리는 좋아 보이는 결과를 자동 경로에서 다시 확인했다

작은 글자와 표 선이 섞이는 문제를 줄이기 위해 긴 표 선을 제거하고, Tesseract의 글자 배치 해석 모드인 PSM을 바꿔 비교했다. 원본과 처리본의 좌표·문구·신뢰도를 모두 남겨, 결과가 좋아 보이는 부분만 선택하지 않도록 했다.

사람이 지정한 작은 영역에서는 개선이 보였다. 전입신고서의 동일한 PSM6 비교에서 지정 키워드 17개 중 포함된 수가 13개에서 16개로 늘었다. 반면 예술인 동의서는 6개 중 4개로 변화가 없었다.

여기서 전처리를 기본값으로 바꾸지 않고 실제 자동 Crop 경로를 다시 실행했다. 기존 탐지 결과와 같은 이미지임을 확인하고 탐지 결과를 재사용해 OCR 설정만 바꿨다.

| 자동 Crop 경로 설정 | 지정 키워드 포함 수 | OCR 단어 수 |
|---|---:|---:|
| 기존 PSM11, 전처리 없음 | 11/15 | 189개 |
| PSM6, 전처리 없음 | 7/15 | 209개 |
| PSM6, 표 선 제거 | 7/15 | 209개 |

수동 영역에서의 개선이 실제 자동 처리에서는 재현되지 않았다. PSM3 설정의 전체 페이지에 표 선 제거를 적용한 별도 실험에서는 전입신고서의 지정 키워드가 15개 중 14개에서 0개로 줄기도 했다. 글자와 선이 겹친 부분까지 손상될 수 있었다.

결국 기본값은 기존 PSM11·전처리 없음으로 유지하고, 표 선 제거는 주변 영역에서 명시적으로 선택하는 비교·검수 옵션으로 남겼다. 수동 영역의 17개와 자동 경로의 15개는 비교 기준이 달라 서로 직접 비교하지 않았다. 어느 수치도 OCR 문자 정확도나 최종 안내 정확도를 뜻하지 않는다.

이 실험에서 가장 크게 배운 점은 **부분 실험의 개선을 실제 사용 경로까지 확인해야 한다**는 것이다. OCR 단어가 189개에서 209개로 늘었어도 필요한 키워드는 줄었다. 더 많은 결과를 반환하는 것과 필요한 정보를 정확히 얻는 것은 달랐다.

한편 같은 행의 단어가 작은 y 좌표 차이로 뒤섞이는 문제는 읽기 순서를 행 단위로 묶어 수정했다. 이때 원래 단어와 신뢰도는 바꾸지 않았다. 인식 결과를 수정하는 작업과 결과를 올바른 순서로 연결하는 작업을 구분했다.

## 7. 검수와 실패 처리를 실제 기능으로 만들었다

지원 문서와 정답이 아직 부족한 상황에서도 개발을 진행하기 위해, 공통 처리와 사람이 확인하는 도구를 함께 만들었다.

촬영 품질 검사에는 해상도·밝기·흐림·경계·기울기 기준을 넣었다. 외부 탐지 전송에는 검토한 마스킹 계획이나 개인정보 없는 빈 양식이라는 명시적 확인을 요구했다. 텍스트에서 개인정보를 검사하는 기존 기능이 이미지 전체의 전송까지 보호하지는 못하기 때문에 이미지 단계의 검사가 따로 필요했다.

마스킹은 자동 개인정보 탐지가 아니라, 사람이 지정한 영역을 같은 이미지에 적용하는 방식으로 구현했다. 이미지가 달라졌는데 예전 박스를 그대로 쓰면 다른 부분을 가릴 수 있어 이미지 지문과 크기를 함께 검사했다.

정답 박스는 원본 위에서 추가·수정·삭제하고 클래스를 바꿀 수 있도록 했다. 처음에는 박스를 바꾸다가 다른 박스를 선택하면 적용하지 않은 수정이 사라지는 문제가 있었다. 선택 변경과 저장 전에 미적용 수정이 있는지 검사하도록 고쳤다.

승인된 COCO 정답에 해시를 기록하는 것만으로도 충분하지 않았다. 평가기가 그 해시를 확인하지 않으면 승인 후 좌표를 바꾼 정답도 평가에 들어갈 수 있었다. 그래서 평가 시에도 내용 해시·원본 파일 지문·이미지 크기를 대조하도록 연결했다. 다만 이 해시는 변경 감지 수단이며, 사람이 올바르게 라벨링했다는 사실이나 검토자의 신원을 증명하지는 않는다.

음성 출력은 우선 macOS의 `say`와 한국어 음성을 이용했다. 별도의 음성 모델을 학습하기보다 원문이 재생·정지·반복 과정에서 유지되는지 검증하는 데 집중했다. 가상 문서로 약 18.8초의 실제 음성 파일을 만들었고, 테스트에서는 마지막 문장과 공백·줄바꿈이 음성 엔진 입력까지 보존되는지 확인했다. 실제 사용자 청취 검증은 별도로 남았다.

이 과정에서 ‘기능이 연결됐다’는 기준도 달라졌다. 지원하지 않는 문서, 미승인 원문, 낮은 신뢰도, 모호한 항목은 성공 결과를 만드는 대신 중단해야 했다. 검토 승인만으로 기존 인식 경고가 사라지지 않도록 한 이유도 같다.

## 8. 로컬 통과와 실행 환경 검증은 별개의 일이었다

외부 API나 실제 장치 없이도 핵심 로직을 확인할 수 있도록 합성 이미지와 가짜 탐지·OCR·음성 응답으로 테스트했다. 마지막 전체 실행에서 1,625개가 통과했다.

개발용 RAG 연산에서는 이전 전체 테스트에 경고가 90건 발생했었다. 고정 입력으로 재현했을 때 기존 내적 연산에서 경고 3건이 발생했고, 동등한 연산 방식으로 바꾼 뒤 0건이 됐다. 최대 수치 차이는 약 `2.78e-17`이었고 비교한 검색 순위와 소수점 6자리 점수는 같았다. 경고만 숨기지 않고 결과가 유지되는지 확인했다.

그 후에도 Windows CI에서 테스트 두 개가 실패했다. 로컬에서는 UTF-8로 읽히던 한글 JSON·HTML이 Windows의 기본 `cp1252`로 해석됐기 때문이다. 새 테스트의 파일 읽기에 인코딩 지정을 빠뜨린 것이 원인이었다.

두 곳에 UTF-8을 명시하고 기본 인코딩을 `cp1252`로 바꾼 조건에서도 다시 확인했다. 이후 Windows·macOS·Ubuntu의 네 CI 검사가 모두 통과했다. 이 경험은 **내 환경에서 통과한 테스트와 팀원이 다른 환경에서 실행할 수 있는 코드는 함께 확인해야 한다**는 점을 남겼다.

테스트 통과 수는 코드의 동작과 실패 처리를 확인한 결과다. 실제 문서 정확도, 개인정보 누락 방지, 하드웨어 정밀도까지 확보했다고 해석하지 않았다.

## 9. 지금 돌아보면 무엇을 먼저 했어야 했나

가장 아쉬운 점은 실제 문서 연동을 넓게 실행하기 전에 고정 평가셋과 정답을 충분히 준비하지 못한 것이다. 299페이지를 처리하면서 문제는 많이 발견했지만, 수정 전후의 Precision·Recall이나 OCR 오류율을 같은 기준으로 비교할 수 없었다. 다시 진행한다면 적은 수의 지원 서식을 먼저 확정하고, 원본과 촬영본의 그룹·정답 박스·원문 전사를 함께 준비하겠다.

안내 정책도 더 일찍 데이터 형식으로 확정할 필요가 있었다. 처음에는 임의 생성만 막으면 된다고 생각했지만, 검토된 설명문과 원문 전체 낭독은 다른 요구였다. 원문 보존 범위, 읽기 순서, 승인 단위까지 정하자 구현과 검수의 기준이 분명해졌다.

반면 유지할 판단도 있다. 낮은 신뢰도를 올려 실행을 통과시키지 않은 것, 정답이 없으면 지표를 측정 불가로 남긴 것, 자동 경로에서 효과가 없는 OCR 전처리를 기본 적용하지 않은 것은 이후 결과를 설명하는 데 도움이 됐다. 남아 있는 문제를 성공 결과로 가리지 않고 다음 작업으로 연결할 수 있었다.

현재는 문서 후보 4종의 안내 초안 9개와 참조 박스 초안 17개를 준비했고, 탐지·OCR·원문 검색·음성·검수·평가의 공통 기능을 구현했다. 이 중 기존 3종의 안내 4개는 원문 전사 전 상태여서 운영 낭독에 사용할 수 없다. 운영용으로 승인된 안내 항목은 아직 0개다. 전입신고서도 원문 읽기 순서와 정답 박스 검수를 마쳐야 하며, 실제 문서의 자동 식별·항목 연결과 별도 촬영본 평가가 남아 있다. 실제 펜 장치와 음성 입력의 사용 환경 검증도 아직 완료하지 않았다.

다음에는 전입신고서 한 종의 원문·정답·안내 연결을 먼저 끝내고, 설정을 고정한 뒤 별도 촬영본으로 평가하려고 한다. 지원 문서를 늘리는 판단은 그 결과와 실제 사용자 확인을 바탕으로 내릴 것이다.
